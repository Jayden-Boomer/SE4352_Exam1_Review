Module 1

What is Software Architecture?

Architecture captures the system’s significant, hard-to-change decisions and its global organization. It focuses on components/elements, their relationships/interactions, constraints, interfaces, responsibilities, and quality attributes.

  • Architecture is early: early architectural decisions are among the hardest to change and are where quality attributes first become explicit.
  • Formal definitions emphasize components/elements, relationships/interactions, externally visible properties, and principles/constraints.
  • Architecture defines structure, component interfaces, component responsibilities, and communication/control flow.
  • Architecture addresses non-functional requirements (NFRs), including technical constraints, business constraints, and quality attributes.
Source: Module 1, slides 7–11 and 37–40
Module 1

Building Architecture Analogy

Buildings help explain architecture because they have identifiable major elements, composition, arrangement, needs, and an architect role—but software differs in important ways.

  • Building architecture is visible; software architecture usually is not directly visible by inspection.
  • Software is not constrained by physical laws in the same way buildings are.
  • Software construction is less mature as an engineering discipline than building construction.
  • Software is dynamic and changes during execution and over its lifetime.
Source: Module 1, slides 3–5
Module 1

Development Models

The course contrasts Waterfall, Iterative/Agile, and Spiral development in how they handle requirements, feedback, iteration, and risk.

  • Waterfall: sequential phase progression; works best when requirements are stable, but late change can be expensive.
  • Iterative: assumes the system cannot be completely understood before construction; uses incremental deliveries and customer evaluation.
  • Agile: emphasizes adaptability, people, short iterations, frequent feedback, and changing requirements.
  • Spiral: combines iteration with waterfall-like structure and places especially high emphasis on risk analysis.
Source: Module 1, slides 24–30
Module 1

Architecture vs. Design

All architecture is design, but not all design is architecture. Architecture is broad and shallow; detailed software design is narrow and deep.

  • Architecture covers the overall system and decisions that are difficult or impossible to change after the system is built.
  • Architecture often concentrates on non-functional requirements and partitions functional responsibilities.
  • Detailed design focuses more deeply on how individual components accomplish functional requirements.
  • The boundary can blur, but scope and level of abstraction are the key distinction.
Source: Module 1, slides 31–34
Module 2

Core Definition: Structures, Views, Abstraction

Software architecture is the set of structures needed to reason about a system; those structures comprise software elements, relations among them, and properties of both.

  • A structure is a set of elements held together by a relation.
  • A view represents a coherent set of architectural elements and one or more structures.
  • Architecture deliberately suppresses internal implementation details that do not matter for system-level reasoning.
  • Different structures support reasoning about different quality attributes.
Source: Module 2, slides 5–16 and 23
Module 2

Programming in the Large

Software architecture is especially useful for programming in the large: systems with many people, many components, and substantial coordination complexity.

  • Programming in the small: simple standalone programs; coordination is limited.
  • Programming in the large: many developers and components; interfaces, dependencies, quality attributes, and communication become major concerns.
  • Architecture supplies abstractions and shared decisions that allow teams to reason about the larger system.
Source: Module 2, slide 27; Assignment 2, Q1
Module 2

Architect Role and AIC

Architects connect technical design to stakeholder needs, organizational constraints, project management, and the technical environment.

  • Typical responsibilities include stakeholder liaison, technology knowledge, software engineering, and risk management.
  • Architects work with requirements teams, stakeholders, technical design teams, and project management.
  • AIC diagram: stakeholders and the development organization influence requirements; the technical environment and architect’s experience also influence the architect.
  • The architect creates the architecture; architecture shapes the system; the resulting system/experience feeds back into future architectural decisions.
Source: Module 2, slides 28–34
Module 3

Architecturally Significant Requirements (ASRs)

An ASR is a requirement that has a profound effect on the architecture. Not every requirement is architecturally significant.

  • Requirements documents and user stories are obvious places to look, but they often emphasize functionality over quality attributes.
  • Architects must frequently work while requirements are still in flux.
  • Stakeholder interviews can reveal architectural drivers and prioritized quality-attribute scenarios.
  • ASRs often come from business goals, not just formal requirements documents.
Source: Module 3, slides 3–9
Module 3

Quality Attribute Workshop (QAW)

A QAW is a facilitated, stakeholder-focused method for generating, prioritizing, and refining quality-attribute scenarios before the architecture is complete.

  • 1. Presentation & introductions
  • 2. Business/mission presentation
  • 3. Architectural plan presentation
  • 4. Identify architectural drivers
  • 5. Brainstorm scenarios
  • 6. Consolidate similar scenarios
  • 7. Prioritize scenarios
  • 8. Refine top scenarios into source–stimulus–artifact–environment–response–response measure form
Source: Module 3, slides 10–12
Module 3

Business Goals & Utility Trees

Business goals frequently lead to ASRs. Utility trees organize and prioritize quality-attribute requirements as scenarios.

  • Business goals may lead to quality-attribute requirements, directly affect architecture without a QA requirement, or have no architectural influence.
  • An ASR should have profound architectural impact and high business/mission value.
  • A utility tree starts at 'Utility', branches into broad quality attributes, refines them, and uses scenarios as leaves.
  • Scenarios are prioritized by business importance and architectural difficulty/impact.
Source: Module 3, slides 13–20
Module 4

Why Architecture Matters

The slides give 13 reasons architecture is important, centered on quality attributes, change, analysis, communication, constraints, planning, reuse, and training.

  • Architecture can enable or inhibit driving quality attributes.
  • It enables early prediction of system qualities and helps manage change.
  • It provides a common language among stakeholders and carries fundamental hard-to-change decisions.
  • It constrains implementation, influences organizational structure, supports prototyping, cost/schedule reasoning, reuse, component assembly, design restriction, and training.
Source: Module 4, slides 3–18
Module 4

Change & Quality Attributes

A good architecture makes likely changes local and provides structures that support desired qualities.

  • Local change: modify one element.
  • Nonlocal change: modify multiple elements while preserving the architectural approach.
  • Architectural change: changes fundamental element interactions and can ripple across the system.
  • Examples of architectural quality concerns include performance, modifiability, security, scalability, incremental delivery, and reusability.
Source: Module 4, slides 4–6
Module 4

Guiding Design Decisions & ADD

Architectural design is systematic decision-making. Attribute-Driven Design (ADD) turns architectural drivers into structures.

  • Seven decision categories: allocation of responsibilities, coordination model, data model, resource management, mapping among elements, binding time, and choice of technology.
  • Coordination decisions include who communicates, allowed/prohibited coordination, and synchronous/asynchronous or guaranteed/non-guaranteed communication.
  • Binding time asks when a choice becomes fixed: build time, deployment time, runtime, etc.
  • ADD uses ASRs plus functionality, constraints, concerns, and design purpose to systematically produce architecture.
Source: Module 4, slides 21–31
Module 5

Architectural Patterns

An architectural pattern relates a recurring context and problem to a successful abstract solution with known elements, connectors, topology, and constraints.

  • Patterns/styles are reusable packages of design decisions.
  • Pattern descriptions include context, problem, solution, element types, connectors, layout, and semantic constraints.
  • Pattern choices have tradeoffs; the best pattern depends on quality goals and domain needs.
Source: Module 5, slides 3–5 and 43
Module 5

Layered Pattern

Layers group modules into cohesive service sets with a unidirectional 'allowed-to-use' relation.

  • Every piece of software belongs to exactly one layer.
  • There are at least two layers, commonly three or more.
  • Allowed-to-use relations should not be circular; lower layers do not use higher layers.
  • Strict layering allows a layer to use only the layer directly below it. It improves replaceability/reasoning but can add complexity and performance cost.
Source: Module 5, slides 13–15; Assignment 2, Q2
Module 5

Client–Server

Clients initiate service requests; servers provide centralized or distributed services.

  • Components: clients and servers; connector: request/reply, RPC, network protocol.
  • Useful when shared resources/services need controlled access or centralized management.
  • Strengths: modifiability/reuse through common services; potential scalability/availability with distributed servers.
  • Weaknesses: server bottleneck, single point of failure, costly client/server responsibility changes.
Source: Module 5, slides 17–21
Module 5

Pipe-and-Filter

Independent filters transform streams of data, connected by pipes.

  • Filters are loosely coupled and can often execute in parallel.
  • Pipes preserve sequence and convey data without changing it.
  • Strengths: reuse, composability, adding transformations.
  • Weaknesses: awkward interaction, limited complex shared state, and performance overhead in some cases.
Source: Module 5, slides 23–25
Module 5

Peer-to-Peer

Peers are decentralized, equal computational entities that both request and provide services.

  • No single peer or peer group should be critical to system health.
  • Strengths: distribution, robustness, scalability, resource sharing.
  • Weaknesses: security, consistency, backup/recovery, availability, and latency can be harder to manage.
Source: Module 5, slides 27–30
Module 5

Publish–Subscribe

Publishers announce events; subscribers register interest; infrastructure distributes matching events without producers needing to know consumers.

  • Strength: decouples producers and consumers and supports flexible one-to-many dissemination.
  • Subscribers can be added without changing publishers.
  • Weaknesses include latency, less predictable delivery time/order, and no guaranteed delivery unless extra mechanisms are added.
Source: Module 5, slides 32–35
Module 5

Shared Data / Blackboard

Independent components communicate through a shared persistent repository rather than directly with one another.

  • Blackboard systems use independent knowledge sources around a central data store.
  • Useful for complex or heuristic problem solving and evolving solution strategies.
  • Shared data can simplify communication but creates coupling around the repository.
  • Weaknesses: performance bottleneck, single point of failure, and potentially tight data coupling.
Source: Module 5, slides 37–41
Module 5 Case Studies

KWIC Pattern Tradeoffs

The KWIC case study compares the same problem under multiple architectural approaches using five criteria.

  • Criteria: change processing algorithm, change data representation, add functions, performance, and reuse.
  • Shared data: good performance and functional enhancement, poor algorithm/data changes and reuse.
  • Abstract data type: improves data/algorithm change and reuse, but is weaker for functional enhancement.
  • Implicit invocation: supports algorithm/function change and extensibility but has weaker performance/control predictability.
  • Pipe-and-filter: strong for algorithm/function change and reuse, but weaker for interactive behavior and performance.
Source: Module 5 Extra, slides 6–15
Module 5 Case Studies

Mobile Robotics Tradeoffs

The mobile robotics case study shows that no single pattern wins everywhere; architecture is chosen based on the required qualities.

  • Control loop: simple and suitable for small reactive robots but limited for complex task decomposition.
  • Layered: organizes abstraction and responsibilities, but real-time communication may not match clean layer boundaries.
  • Implicit-invocation task control: strong for complex coordination, fault tolerance, safety, and incremental replacement.
  • Blackboard: supports coordination and uncertainty resolution through a shared repository.
Source: Module 5 Extra, slides 26–44

05 · Fast Study Plan

A high-yield review sequence

Prioritize connections between requirements, quality attributes, design decisions, and pattern tradeoffs.

1. Foundations

Architecture definition → structures/views → abstraction → broad/shallow vs. narrow/deep → programming in the large.

2. Drivers

ASRs → stakeholders → QAW → business goals → utility trees → quality-attribute scenarios.

3. Decisions

Why architecture matters → local/nonlocal/architectural change → seven decision categories → ADD.

4. Patterns

Learn each pattern as: context/problem/solution + components/connectors/constraints + strengths/weaknesses.

5. Tradeoffs

Use KWIC and robotics to practice answering “why this pattern for these quality goals?” rather than memorizing one universally best style.

6. Written responses

Practice a 4-part answer: define → explain mechanism → give example → name tradeoff/limitation.
